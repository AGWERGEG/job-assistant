# RC4.3.17 BOSS HR 会话串读与 JD 招聘者状态修复测试版

Edge 现场显示，陈先生会话位于联系人首位；侧栏读取的招聘者、企业、岗位正确。会话“查看职位”打开的岗位 ID 与工作台已保存 JD 相同。JD 页招聘者标题显示“陈先生 在线”。旧采集器会将 `.job-boss-info .name` 的状态字一起保存为招聘者姓名；后端严格比对时，“陈先生 在线”与聊天页的“陈先生”不一致，却只向界面返回“没有找到匹配的已建档 JD”。

用户随后提供了另一条直接证据：选中的聊天头部是“李先生／点众科技／HR招聘”，侧栏却显示“郭芮／有赞”，且岗位字段拼入了李先生的头部。隔离 DOM 复现了完全相同的错误结果。原因是旧提取器不识别“HR招聘”，在查找当前职位条的头部失败后继续回溯父容器，并从前一个容器的子节点中取到左侧联系人“郭芮”。

本版同时处理两条已复现路径：新 JD 采集去掉招聘者姓名末尾独立的“在线/离线”状态；匹配历史已存记录时也去掉该状态，用户无须重建 JD。聊天页只使用当前职位条的紧邻头部，不再搜索前一个容器里的联系人；支持“HR招聘”等招聘者职务，并拒绝把头部混入岗位标题。岗位平台 ID、企业、岗位名称和其余招聘者姓名核验维持原规则，历史资料不批量修改。

隔离 DOM 重现了状态词进入采集字段，以及“郭芮／有赞”串入“李先生／点众科技”的错误；隔离 Bridge 测试验证旧字段可绑定、其他姓名仍拒绝。Python 全量 122 项通过；`test_chat_context.cjs`、`test_extension.cjs`、`test_workspace.cjs` 全部通过。

尚未在用户现有数据上读取历史招聘者字段，也未加载同版 Edge 扩展与服务复测这两条会话。若新版仍显示无匹配，应先核对侧栏当前会话的姓名、企业、岗位，再检查后端具体拒绝原因。
