# 三个核心功能的返回速度优化

## 已记录的独立精确页问题

独立精确页偶发无法识别已记录在 `KNOWN_ISSUES.md`，本轮暂不处理。

## 慢的原因

按钮点击到结果显示包含四段：任务创建、队列等待、启动新的 Codex CLI 会话、模型生成完整 JSON。历史任务数据中，已完成任务常见耗时约 140–260 秒；其中任务创建和侧栏轮询不是主要瓶颈，主要等待来自独立 Codex 推理和单 worker 串行排队。

## 本轮改动

1. 默认 worker 使用 `gpt-5.6-luna` 与 `low` 推理档，面向“先给可用初稿”的侧栏交互。
2. 默认启动 2 个并行 worker，避免自动岗位判断阻塞手动“改简历/准备回复”。SQLite claim 仍保证每个任务只被一个 worker 领取。
3. worker 空闲轮询从 2 秒降为 0.5 秒，减少任务入队后的额外等待。
4. 后续“改简历/准备回复”只携带上一轮结果的决策、策略和有界草稿，不再把多份 12000 字详细说明完整塞回模型上下文。
5. 保留可调参数：
   - `--workers 1` 或 `JOB_ASSISTANT_WORKERS=1`
   - `JOB_ASSISTANT_CODEX_MODEL=gpt-5.6-sol`
   - `JOB_ASSISTANT_CODEX_REASONING=medium`

## 预期与边界

这版先优化首个可用结果的等待时间，不承诺固定秒数。模型服务、账户额度、岗位/JD 长度和本机网络仍会影响总耗时。扩展侧栏目前每约 2.5 秒轮询一次任务结果；这只是显示延迟，不能替代模型推理时间。

在当前本机账户的隔离虚构任务实测中，`gpt-5.6-luna + low` 的一次岗位判断约 136 秒；因此本轮不能宣称已经达到“秒回”。如果仍需显著低于 1 分钟，下一阶段应接入专用低延迟模型/API 或常驻推理会话，而不是继续堆叠浏览器轮询。

## 测试方式

启动时查看工作台顶部“自动分析已开启”，并用浏览器开发者/任务列表记录任务 `created` 到 `updated` 的差值。对同一岗位重复点击会复用缓存，不应再次调用模型。
